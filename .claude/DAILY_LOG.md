### 🚚 Pedidos por WhatsApp + Domicilios: del texto libre a una dirección real (pedido del socio)

Diagnóstico rápido del estado actual (`instance-manager/agents/gemini.js` y `api/routes/domicilios.js`): hoy el bot detecta una dirección dentro del mensaje del cliente con un regex heurístico (`pareceDireccion()`), la guarda tal cual como texto libre en el pedido, y ahí termina — no hay geocodificación, ni confirmación con el cliente, ni coordenadas, ni ruta, ni cálculo de tarifa por distancia (`tarifa_envio` es un valor fijo hardcodeado en `$5,000` en `POST /api/domicilios`, y la columna `km_recorridos` existe en la tabla pero **ningún endpoint la llena** — siempre queda en 0). Tareas para cerrar esa brecha, en orden de dependencia:

- [x] **Geocodificar la dirección del pedido — hecho.** Migración `db/migrate_geocoding.js`: columnas `pedidos.direccion_lat`/`direccion_lng` y `negocios.lat`/`lng` (esta última para la tarea de tarifa por km, se agregó de una vez). Nuevo `instance-manager/services/geocoding.js` que llama a `POST` — en realidad `GET /v4/geocoding/search` de TravelTime (la misma cuenta de los mapas, pero esta vez sí hace falta la Api Key además del App Id — guardadas ambas en `antigravity/.env`, la Api Key nunca va al frontend). Conectado en `orchestrator.js` → `crearPedido()`: después de insertar el pedido, si hay `direccion_entrega`, geocodifica (usando `negocio.ciudad` como contexto para desambiguar) y guarda lat/lng; si falla, no bloquea la creación del pedido/domicilio. Un detalle que costó encontrar: el `fetch` nativo de Node mandaba un header `Accept-Language` que TravelTime rechazaba con 400 (`Invalid language code`) — se fuerza `Accept-Language: es-CO` explícito. Probado end-to-end llamando `orchestrator.ejecutarAccion()` directo (sin pasar por WhatsApp) con una dirección real de Bogotá — coordenadas correctas guardadas en `pedidos`; pedidos de prueba borrados después. Nota importante: el campo `score` que devuelve TravelTime **no sirve para filtrar automáticamente** direcciones inventadas (una dirección basura dio score 0.31 y "asdf" dio 0.76, más alto que una dirección real con 0.44) — la mitigación real para direcciones mal escritas es la tarea de abajo (que el bot confirme con el cliente), no un umbral de confianza acá.
- [x] **Que el bot confirme la dirección antes de crear el pedido — hecho (20 sept).** En `gemini.js`, nuevo `manejarFlujoDireccion()`: con domicilios activos, cuando el cliente (ya en proceso de compra, para no interceptar preguntas tipo "¿están en la carrera 8?") manda una dirección, el bot responde de forma **determinista, sin gastar tokens de IA**: `📍 Entendí esta dirección: *...* ¿Es correcta? Responde *sí*...`. El estado vive en el propio historial (el mensaje del bot lleva ese marcador fijo, no hacen falta columnas nuevas). "Sí" → recién ahí se crea el pedido con la dirección confirmada (y se guarda en `clientes.direccion_guardada`); "no" → pide la dirección de nuevo; una dirección corregida → se vuelve a confirmar. Se refactorizó `construirAccionPedido` (helpers `resolverProductos`/`esMensajeConfirmacion`). Probados los 4 escenarios llamando `gemini.procesarMensaje` con historial simulado. Ya no se crea ningún pedido con una dirección que el cliente no confirmó.
- [x] **Calculadora de tarifa por km — hecha (20 sept).** Nuevo `instance-manager/services/routing.js` (ruteo por calles con TravelTime `POST /v4/routes`: distancia real, tiempo y geometría; si falla cae a línea recta × 1.3) y `domicilioTarifa.js` (`calcularCondicionesDomicilio`, usado por el bot y por `POST /api/domicilios/crear`).
